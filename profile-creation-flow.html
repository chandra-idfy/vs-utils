Creating a Profile

Profile creation is the system's most exercised flow. Seven HTTP entry points funnel into one domain function, which atomically inserts a row, materialises tasks from a JSONC package definition, advances a state machine, and fans out side effects (artifacts, notifications, webhooks, RMQ events). This page traces every stage with file:line citations.

snapshot · master · 5b387331b

1 · Overview

A profile represents one customer's KYC journey. Creation is split between a synchronous "insert + validate" core and a post-create phase that can run inline (sync) or under a Task.Supervisor (async).

4 · The Pipeline, Step by Step

The full creation flow has eight stages. Each card lists what runs, the file:line, and the "why".

Filters the cards below in real time. Hit Esc to clear.

  1. OU resolution & payload pre-processing PLUG

    Before any controller code runs, plug pipelines resolve the tenant, optionally decrypt the body, and reject malformed/oversized payloads.

    • Cust.set_organization_unit — reads x-idfy-ou-id, looks up OrganizationUnit, assigns to conn.assigns.organization_unit; 400 if not found and halts.
    • EncPlug.decrypt_payload (encrypted routes only) — calls PayloadEncryption.decrypt_create_profile_params; replaces conn.params with decrypted body; 422 on failure.
    • BulkUpload.set_organization_unit_bp (bulk routes) — same as Cust but stamps x-correlation-id into Logger.metadata.
    • ValidatePayload — scans body for malicious chars / oversized fields, gated by ENFORCE_MALICIOUS_CHARS_CHECK and ENFORCE_PAYLOAD_CHAR_LIMIT env vars.
    • x_request_id — assigns/propagates correlation ids into Logger metadata.
    plug/cust.ex:17 plug/enc.ex:9 plug/bulk_upload.ex:16 plug/validate_payload.ex:16

  2. Controller dispatch CTRL

    The controller action enriches the request map with OU context and a flow_source tag ("api_sync", "api_async", "invite"), delegates to RequestParser, then calls into the domain.

    # profile_controller.ex:169
def create_sync(conn, profile_params) do
  ou = conn.assigns.organization_unit
  with {:ok, params, artifacts} <-
         RequestParser.parse_request(profile_params, ou,
           %{validate_security_questions: true}),
       params = Map.merge(params, %{
         organization_unit_id: ou.id, ou_id: ou.ou_id, ou_config: ou.configuration
       }),
       {:ok, profile} <-
         Profiles.create_profile_sync(params, artifacts, %{flow_source: "api_sync"}) do
    render(conn, "profile_sync.json", profile: profile)
  end
end
    profile_controller.ex:169 profile_controller.ex:216 profile_controller.ex:242

  3. Request parsing & package validation

    RequestParser validates structure, looks up the package by public_id, materialises artifact intents (downloads URLs, validates types) in parallel via Task.async_stream, and runs the package's profile-creation rules.

    • Validates data is a map and reference_id is binary.
    • Packages.get_by_public_id/1 — resolves the JSONC-defined package definition.
    • RuleEngine.evaluate_profile_request/2 — enforces package-defined entry rules (e.g. tag whitelist, link-expiry sanity, security-question count, accessibility type).
    • Returns {:ok, profile_params, artifact_objects} or {:error, :unprocessable_entity, %{error, details}}.
    • If any artifact URL fetch times out (30s), the whole call halts with "DOCUMENT_FETCH_TIMED_OUT".
    profiles/request_parser.ex:158 packages.ex:144 rule_engine.ex:1

  4. Idempotency & identifier generation

    Two layers protect against re-creating the same profile:

    • Archived dedupe — ArchivedProfiles.get_profile_by_reference_id blocks reuse of a reference_id that was previously purged.
    • DB unique constraint — composite index profiles_reference_id_organization_unit_id_index rejects duplicates per OU at insert time (surfaced as an Ecto.Changeset error).
    • public_id — generated by Ecto.UUID.generate() server-side, so the API caller never controls it. :autogenerate is set on the schema field.
    • Once created, a reference_id can be reassigned via the cancel_and_change_reference_id flow (out of scope for this page).
    profiles.ex:462 profiles/profile.ex:123 profiles.ex:459

  5. Encrypted insert via the custom Repo

    The DB write goes through Repo.insert_sm/1, not vanilla Ecto. This wrapper (a) refuses to accept a manually-set status in the changeset, and (b) routes through insert_enc/2, which pulls a per-OU DEK from PII Service and encrypts the configured fields before the row hits Postgres.

    • Encrypted fields: request_body, response_body, manual_response, automated_response, location, object_id, upload_objects.
    • DEK source: Encryption.get_encryption_key_and_encrypt_data/2 calls ENCRYPTION_KEY_URL when ou.configuration["send_to_pii"] is true.
    • Initial state: the schema default "pending" is the only value Repo.insert_sm permits at insert.
    • Returned value is decrypted before the function returns.
    repo.ex:55 utils/encryption.ex:129 payload_encryption.ex:270

  6. post_create_profile fan-out

    Once the profile row exists, post_create_profile/3 orchestrates everything else. In SYNC mode this runs inline on the request thread. In ASYNC mode create_profile_async spawns it under Task.Supervisor.start_child(KycGatewayBackend.TaskSupervisor, fn -> … end) and returns immediately.

    • Artifacts: create_profile_artifacts/2 via Task.async_stream, 30s timeout per artifact.
    • Validation checks: create_validation_checks/2 — package-level checks materialised as Tasks (parallel).
    • Pre-checks: create_pre_checks/3 — capture-phase tasks (sequential; some are immediately initiated, not just created).
    • Status transition: update_profile/2 sends the profile to "capture_pending" if package.capture_enabled, else "in_progress".
    • State-machine side-effects fire here (capture creation, notifications, webhooks, RMQ — see §6).
    profiles.ex:3684 profiles.ex:3894 profiles.ex:3934

  7. Task & capture materialisation

    Tasks are created eagerly inside a single Repo.transaction/1 by TaskFactory.build_and_create_task/3. Each task starts in "pending"; outbound provider calls only fire after a task transitions to "queued". The capture record (if any) is created when the profile state machine enters "capture_pending".

    tasks/task_factory.ex:208 tasks/task_state_machine.ex:216 profiles/profile_state_machine.ex:411 captures.ex:1

  8. Response shaping

    The view layer renders different payloads depending on the entry point:

    • profile_sync.json — full body with capture link & expiry (when capture_pending).
    • profile_async.json — minimal stub (profile_id, reference_id, status).
    • invite.json — dashboard-shaped payload.
    • ResponseHandler.generate_response/3 branches on package version for backwards-compat tag handling.
    profiles/response_handler.ex:20 views/profile_view.ex:1

What the machine does at creation time

  1. Insertion: status = pending

    Repo.insert_sm rejects any changeset that explicitly sets status. The schema default "pending" is the only legal initial value.

    repo.ex:55 profiles/profile.ex:19

  2. Transition: pending → capture_pending | in_progress

    Inside post_create_profile, after artifacts and tasks are materialised, update_profile/2 calls Repo.update_sm/2, which routes through the state machine. Two callbacks matter:

    • before_transition(_, _, "capture_pending") — calls Profiles.create_capture/1 to mint the capture record + session token; uses auth_token_expires_at from package config or OU override.
    • after_transition(_, _, "capture_pending") — emits the profile-create webhook (sync if SEND_PROFILE_UPDATE_WEBHOOKS_IN_SYNC, else TaskSupervisor), triggers ProfileNotification.profile_creation (SMS via MESSAGE_ENGINE_BASE_URL), increments the Redis profile counter, optionally publishes to the ProfilesPublisher RMQ exchange (gated by ENABLE_PROFILES_PUBLISHER).
    profile_state_machine.ex:411 profile_state_machine.ex:96 profile_notification.ex:264
i
Why two-phase? The machine wants tasks/artifacts/captures to exist before the profile leaves pending. Going straight to in_progress at insert would race the post-create work and let webhooks fire with no resources attached.

8 · Tasks & Captures during creation

A profile is just the parent. The actual verification steps live in Task rows — created from the package definition during creation, dispatched to external providers later.

Where Tasks come from

  1. Package lookup

    Already done in step 3 of the pipeline. The resolved %Package{} carries capture_configuration, assisted_vkyc_configuration, self_vkyc_configuration, review_configuration, generic_page_configuration, video_tasks, pre_checks, post_checks.

    packages/package.ex:34

  2. Parser fan-out

    Parser.parse_package/1 async-streams six specialised child parsers (capture, AVKYC, review, SVKYC, generic-page, video). Each returns normalised task templates.

    packages/parser.ex:83

  3. Task materialisation in one transaction

    TaskFactory.build_and_create_task/3 wraps everything in Repo.transaction/1. Parent + child tasks insert together; either the whole tree appears or none of it does. Each task starts at "pending".

    tasks/task_factory.ex:208

  4. Sequencing via deps

    Tasks don't have a page_sequence; ordering is implicit via the deps array (task keys that must complete before this one is allowed to queue) and the parent_task_id hierarchy. Tasks.can_queue?/1 resolves readiness at runtime.

    tasks/task.ex:53 tasks/task.ex:60

  5. External dispatch — only on queued

    Outbound calls (API Gateway, AssistedVKYC, SelfVideo, TrueSight, DocumentFetcher, IDfy360, …) fire from the task state machine's after_transition(_, _, "queued") hook, never at insert time.

    tasks/task_state_machine.ex:216 tasks.ex:5595

Capture record

The captures row is materialised lazily by Profiles.create_capture/1 when the profile transitions into capture_pending. Holds: public_id, session_token, auth_token_expires_at, status: "pending". The capture link the customer gets in the webhook is built from these fields.

9 · Encryption Layer

Two distinct encryption concerns intersect during creation: transport (the client's encrypted body) and at-rest (per-OU DEK applied at the Repo layer).

TRANSPORT

Encrypted endpoints

Routes under /ext/cust/enc/* add the :encrypted_endpoint pipeline. The EncPlug.decrypt_payload plug calls PayloadEncryption.decrypt_create_profile_params(body, ou_id) and replaces conn.params with the plaintext.

  • Per-OU public key advertised at /ext/dashboard-backend/public-key
  • Key rotation via POST /ext/cust/enc/rotate_key
  • Failure shape: 422 with %{error: "..."}
plug/enc.ex:9 payload_encryption.ex:1
AT-REST

Repo-level encryption

Repo.insert_sm / Repo.update_sm intercept Profile, Artifact, Task, Snapshot writes and run them through insert_enc / update_enc. PII Service (ENCRYPTION_KEY_URL) returns the OU's DEK when ou.configuration["send_to_pii"] is true; otherwise the data goes in raw.

  • Encrypted columns: request_body, response_body, manual_response, automated_response, location, object_id, upload_objects
  • DEK rotation via rotating_encryption_key/2 sets expiry on the prior active key
  • Active KeyStore lookup keyed on (ou_id, key_id, deleted_at IS NULL)
repo.ex:55 utils/encryption.ex:129 payload_encryption.ex:122
⚠
Never go around the Repo. Direct Postgrex / Ecto.Repo.insert on Profile/Artifact/Task/Snapshot stores plaintext PII and breaks the next read because decryption metadata is missing.

11 · Gotchas & Edge Cases

  • DANGER
    Never set status in a profile changeset. Repo.insert_sm raises if you do — it owns lifecycle. Always go through Profiles.update_profile/2 or a state-machine event helper.
  • DANGER
    Don't bypass the custom Repo for Profile/Artifact/Task/Snapshot. Bypassing skips encryption — PII lands in plaintext and reads will fail.
  • CARE
    Async creation hides post-create errors. A 202 guarantees the row exists, not that artifacts/tasks/notifications succeeded. Check the profile.status after creation, and rely on the failure webhook to detect post-create issues.
  • CARE
    Artifact URLs run inside Task.async_stream with a 30 s timeout per artifact (profiles.ex:4290). Slow customer URLs make creation slow — consider async creation when calling profiles need pulled documents.
  • CARE
    Side-effect feature flags don't necessarily run locally. ENABLE_PROFILES_PUBLISHER, ENABLE_TRUESIGHT_PUBLISHER, SEND_PROFILE_UPDATE_WEBHOOKS_IN_SYNC, PROFILE_TRANSITION_LOCK_V2_ENABLED all gate consumers/producers in application.ex. Check application.ex:36 before assuming a publisher fires.
  • CARE
    Reference id collision is rejected at the DB layer, not the parser. The parser passes a duplicate through; the unique index profiles_reference_id_organization_unit_id_index raises a constraint error in Repo.insert_sm and surfaces as an Ecto.Changeset 422.
  • CARE
    Encrypted endpoints share the action. /ext/cust/sync/profiles and /ext/cust/enc/sync/profiles hit the same create_sync function. The only difference is whether EncPlug.decrypt_payload ran. Don't add encryption-specific logic in the controller — it'll only run for the enc variant, never the plain one.
  • NOTE
    The dashboard invite path uses different decryption. It does not use :encrypted_endpoint; it reads kid + dh headers and calls Crypto.decrypt directly inside the action. Then routes to the same create_profile_sync with flow_source: "invite".
  • NOTE
    No profile_action row is written at creation. Don't filter activity dashboards expecting one. Manual reviewer/agent actions create those rows.
  • NOTE
    Task creation is transactional, profile creation is not. The profile insert and post-create work happen in separate connections — if task creation fails, the profile already exists in "pending". The recovery path is send_webhook(profile, :error) + manual intervention via the scripts/ retrigger files.
  • NOTE
    Capture link lifetime comes from two places. Package capture_configuration.auth_token_expires_at is the default; OU configuration can override per-tenant. Resolved during the capture_pending transition.
  • NOTE
    Bulk-upload uses a different OU resolution plug. SetOrganizationUnitBp reads ou-id (no x-idfy- prefix) and adds x-correlation-id Logger metadata. Don't paste the bulk request shape into the regular /ext/cust path — the headers won't resolve.

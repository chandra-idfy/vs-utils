The package parser, in plain English

Forget the syntax for a moment. Here's what the parser does and how its function calls actually flow when someone saves a package.

The 30-second story

Imagine an admin uploads a long, complicated form — a "package" describing how a KYC flow should work for a specific bank. It has dozens of sections: which photos to capture, which checks to run, which review steps to show, which notifications to send.

Before saving it, we need to make sure every section is well-formed and that the sections don't contradict each other. Doing this one section at a time would be slow, and stopping at the first error would frustrate users.

So the parser splits the form into pieces, hands each piece to a specialist who knows that section's rules, runs them all at the same time, and collects every complaint into one big list. Only if every section is individually clean does it run a second round of checks looking for inconsistencies between sections.

What happens when someone saves a package

A walk-through of the function call chain — what gets called, in what order, and why.

HTTP request lands at the controller

An admin clicks "Save" in the dashboard. The package JSON arrives at PackageController.create or .update. The controller's only job is to hand it off to the domain layer.
PackageController → Packages.validate_package(json, ou_id)
↓

The Packages context calls the parser

The Packages context module is the public face of the domain. It calls into the parser to do the heavy lifting.
Packages → Parser.validate_package(package, ou_id)
↓

Parser starts a small "memo pad" to share between workers

Because the parser is going to run many checks at the same time, none of them can see each other's work directly. So the parser spins up a tiny background process called an Agent that holds shared notes — mostly a list of "task keys" each worker has discovered, plus the OU id.
Agent.start_link(fn -> %{"task_key" => %{}, "task_type" => %{}, "ou_id" => ou_id} end)
↓

Wave 1 fires — 17 checks at once

The parser builds a list of 17 functions, each one validating a different section of the package. It then calls Task.async_stream which is Elixir's way of saying "run all of these in parallel and collect the results."
Each function calls a specialist parser:
  • parse_config(capture_configuration, ...) — walks the capture tree
  • CaptureParser.validate_feature_flags(...) — checks capture flags
  • AssistedVideoParser.validate_feature_flags(...) — AVKYC flags
  • parse_locale_config(...) — language/locale settings
  • parse_review_configuration(...) — review settings
  • NotificationConfigurationParser.parse_config(...) — notifications
  • …and 11 more, all running at the same time.
Task.async_stream(jobs, & &1.(), on_timeout: :ignore)
↓

Each specialist returns either "okay" or "here are the problems"

Every specialist returns one of two shapes:
  • {:ok, %Meta{}} — "I'm happy. Here's what I learned." (e.g. "this section creates artifacts X, Y, Z")
  • {:error, [error1, error2, ...]} — "Here's a list of every issue I found in my section."
The parser doesn't stop on the first error — it lets every specialist finish and accumulates everything they found.
↓

Decision time: continue or bail out?

If every specialist returned :ok, the parser sets a flag process_continue? to true and moves on to wave 2.
If any specialist returned errors, the parser stops here, packages all the errors into a single map keyed by section name, and returns to the caller.
if process_continue? do (run wave 2) else (return errors) end
↓

Build the meta — what artifacts were created? Referenced?

Before wave 2 runs, the parser merges every %Meta{} the specialists returned into one big metadata map. This records:
  • Created artifacts: things capture produces (PAN front photo, Aadhaar back, selfie, etc.)
  • Referenced artifacts: things later steps expect to use
  • Checks: the count and types of tasks defined
check_and_process_meta(...) |> filter_artifact_based_on_source(...)
↓

Wave 2 fires — 17 cross-section invariants

Now the parser checks things that need multiple sections to be valid:
  • Did every referenced artifact actually get created? If post_checks wants to verify a PAN photo, capture must have produced one.
  • Are task keys unique across sections? Reading the Agent's "memo pad" from step 3.
  • Does the page sequence cover every page?
  • Do AVKYC tasks line up with capture and pre-checks?
  • Are the POI/POA document lists real document types? (hits the database)
  • …and 12 more.
Task.async_stream(jobs, & &1.()) |> Enum.reduce(...)
↓

Final answer goes back to the caller

If wave 2 also passed, the parser stamps the metadata onto the package and returns success. Otherwise it returns the wave 2 errors under an "others" key.
{:ok, package_with_metadata} or {:error, %{"others" => [...]}}

The recursive walker, in plain words

The single most important function inside wave 1 is parse_config/3. It's how the parser actually walks through the deeply nested capture tree.

Think of it as a function that asks "what kind of thing am I looking at?" and reacts accordingly:

Empty?
{}, [], or nil
Just return success with an empty meta. Nothing to do.
A section with "capture"?
%{"capture" => ...}
Validate the section's other knobs (bandwidth, screenshot edit, etc.) and recursively walk into the capture array.
A list?
[item1, item2, ...]
For each item, recurse into parse_config if it's a list, or hand off to object_parser if it's an object. Track the index in the path.
A task or template object?
%{"task_key" => ..., ...}
object_parser takes over and dispatches to TaskParser, TemplateParser, or ArtifactParser depending on what the object looks like.

As it descends, it keeps appending to a path string. So when it hits an error six levels deep, it can produce a message like "task_key missing at capture_configuration.capture.0.1" — the path tells you exactly which JSON node is broken.

Mini glossary

Elixir-isms you'll see in the code, translated to plain English.

{:ok, value} / {:error, reasons}
A two-element tuple, the standard way Elixir functions report success or failure. Like a return code paired with a payload.
Task.async_stream(jobs, & &1.())
Run all the functions in jobs in parallel and stream back the results. Think Promise.all in JavaScript.
Agent.start_link
Spawns a small background process that holds shared mutable state. Other functions read or write to it through messages. Like a thread-safe in-memory key-value store.
%Meta{}
A struct (like a typed dict) holding what each parser learned: artifacts created, artifacts referenced, check counts. Like an accumulator object.
|> (pipe)
a |> f |> g is the same as g(f(a)). Reads left-to-right. Like Unix pipes.
def vs defp
def defines a public function (callable from other modules). defp is private (callable only inside the same module). Like public/private methods.
Multi-clause functions
def parse_config(...) appears multiple times with different argument shapes. Elixir picks the matching one. Like overloading by structure.
"capture" => capture
Map syntax with string keys (because the JSON has string keys). Like {"capture": value} in JSON.
One-line summary: the package parser is a JSON validator that fans out across many specialist checkers in parallel, accumulates every problem instead of stopping at the first, runs section-level checks first and cross-section checks second, and returns either a clean package with metadata or a structured list of every issue found.

Three public entry points

Same module, three life-cycle phases. Each gets the package in a different shape and produces a different output.

1. validate_package(package, ou_id \\ nil)

Called before insert/update. Walks every section, runs ~34 parallel checks across two waves, and returns either the package with attached metadata or a flat list of structured errors.

2. parse_package(package)

Called after insert. Walks the saved record's six top-level sections in parallel and replaces inline "template" => {...} payloads with "template_id" => N references in the templates table.

# lib/kyc_gateway_backend/packages/parser.ex:83
def parse_package(package) do
  package_version = Map.get(package, :version, "v1.3")
  [
    fn -> parse_package_configuration(package.capture_configuration) end,
    fn -> parse_package_configuration(package.assisted_vkyc_configuration) end,
    fn -> parse_package_review_configuration(package.review_configuration) end,
    fn -> parse_svkyc_package_configuration(package.self_vkyc_configuration) end,
    fn -> parse_generic_page_configuration(package.generic_page_configuration) end,
    fn -> parse_video_task_config(package.video_tasks, package_version) end
  ] |> Task.async_stream(& &1.(), timeout: 10_000) |> Enum.map(...)
end

3. get_package_json(%Package{} = package)

Inverse direction. Reads the persisted %Package{} and resolves every template_id back to its full inline template, returning JSON ready for export, audit, or cloning to another OU.

Design symmetry: parse_package and get_package_json are inverses. validate_package guards the front door — nothing reaches the DB without passing it.

The two-wave validation pipeline

Click any job to see what it actually checks. Wave 1 runs first and gates wave 2 — cross-section invariants only run if every section is independently valid.

WAVE 1 Section-level (17 jobs)

All run in parallel via Task.async_stream. Each section is validated independently. If any fails, the whole call returns errors and wave 2 is skipped.

WAVE 2 Cross-section (17 jobs)

Runs only after wave 1 is fully clean. Checks invariants between sections — e.g. that artifacts referenced in post_checks were created in capture_configuration.

Why two waves?

Cross-section invariants assume each section is internally well-formed. Checking task-key uniqueness across sections is meaningless if a section has malformed task keys to begin with. The gate at line 1101 (process_continue?) enforces this.

Concurrency model

  • Each wave fires Task.async_stream with the default max_concurrency = System.schedulers_online().
  • Wave 1 uses on_timeout: :ignore — timed-out jobs become structured errors (line 1077) instead of crashing the call.
  • parse_package and get_package_json use a 10-second per-task timeout.
  • Specialist parsers internally fan out further — nested async_stream over capture arrays.
Hot spot: for very large packages (many tasks/templates), unbounded concurrency means CPU goes wide. Validation TAT is logged via CustomLogger as event_type: "validate.TAT".

The 10 specialist parsers

Each lives under lib/kyc_gateway_backend/packages/parser/. The master parser only orchestrates — the actual rules live in these files.

Why split this way?

The split is by package section, not by check type. CaptureParser owns everything inside capture_configuration; DecisionEngineValidator owns autoclose / risk / propensity / enhanced-review; ArtifactParser validates the dotted artifact-key syntax that shows up in many sections. This means changes to one section rarely touch other parsers.

Adding a new section? Create a new module under parser/, alias it at lines 24–35, and add a job to wave 1 (or wave 2 if it depends on other sections being valid first).

Error model

Every error is a map with two keys — "key" (the section/path) and "message" (a human-readable description). Errors are accumulated: the validator collects every problem in one pass instead of bailing on the first.

Path-threaded errors

Every recursive call carries a path argument that grows as the parser descends:

def parse_config(config, path, agent) when is_list(config) do
  config
  |> Enum.with_index()
  |> Task.async_stream(fn {each_config, index} ->
    parse_config(each_config, "#{path}.#{index}", agent)   # path grows: "capture_configuration.capture.3.tasks.1"
  end)
end

This is why error messages can pinpoint the exact JSON node — you can paste the path straight into a JSON viewer.

Shared state & data flow

Pure functions can't see each other's results when running concurrently. Two pieces of carry-state make cross-section validation possible: a short-lived Agent and a %Meta{} accumulator.

The Agent

# lib/kyc_gateway_backend/packages/parser.ex:950
{:ok, agent} = Agent.start_link(fn ->
  %{
    "task_key"  => %{},   # discovered task keys: name -> type
    "task_type" => %{},   # type counts
    "ou_id"     => ou_id   # scope for OU-aware validations
  }
end)

The Agent is passed into every parse_config call. Specialist parsers running concurrently push the task keys they encounter into it — so when wave 2 runs task_key_validation_process, it can see every task key from every section in one place.

The Meta struct

# lib/kyc_gateway_backend/packages/meta.ex
%Meta{
  created_artifacts:    %{},  # source -> [artifact_keys]
  referenced_artifacts: %{},  # source -> [artifact_keys]
  checks:               %{}   # task_type -> count
}

Every leaf-level parser returns either {:ok, %Meta{}} or {:error, errors}. As recursion unwinds, update_metadata (parser.ex:1394) merges the %Meta{} values like a monoid — lists concatenate, maps deep-merge.

How meta drives wave 2

Wave 2's most important check is check_created_and_referenced_artifacts (line 1513): it walks referenced_artifacts and asserts every entry exists in created_artifacts. If a post_checks task references id.ind_pan.ocr.user.front, capture must have produced it.

# final shape stamped onto the package
%{
  "resources" => %{
    "0" => ["id.ind_pan.ocr.user.front", ...],
    "1" => [...], "2" => [...], "3" => [...], "4" => [...]
  },
  "checks" => %{...task_type counts...}
}
Why the source numbers? "0"…"4" are document sources (user upload, system fetch, etc.) defined in KycConstants. filter_artifact_based_on_source at line 1441 collapses duplicates per source.

Patterns worth knowing

1. Multi-clause dispatch on shape

parse_config/3 uses Elixir pattern matching to route based on the JSON node's shape:

def parse_config(config, _, _) when config in [%{}, [], nil] do ... end             # empty
def parse_config(%{"capture" => capture} = config, path, agent) do ... end      # section node
def parse_config(config, path, agent) when is_list(config) do ... end             # list node

This is the recursive walker that drives the whole thing. Object nodes get handed off to object_parser (line 2406) which dispatches further into TaskParser, TemplateParser, etc.

2. Concurrency with structured timeouts

Task.async_stream(jobs, & &1.(), on_timeout: :ignore)
|> Enum.map(fn
  {:ok, resp}        -> resp
  {:exit, :timeout}  -> {:error, "... timed out"}
  {:exit, reason}    -> {:error, "Async stream process exited: #{inspect(reason)}"}
end)

Crashes and timeouts become structured errors instead of propagating — the validator never raises.

3. Two-phase metadata extraction

check_and_process_meta (line 1356) collapses each section's %Meta{} output into a single combined struct, then filter_artifact_based_on_source (line 1441) deduplicates per artifact source. Only after that does return_package_with_meta stamp it onto the package.

4. Inverse pair: extract and re-attach templates

JSON in -> parse_package     -> # strip inline templates -> Template table
        DB rows                          %Package{} with template_id refs

DB row -> get_package_json -> # reattach inline templates
        JSON out                         canonical export shape
